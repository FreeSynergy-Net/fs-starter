# FreeSynergy starter

FreeSynergy starter: the host that starts a program from its blueprint package (`scaffold.toml` + `forms/` + texts) without compiling it. The host owns the parts that are the same in every program (session, update, appearance, help, the MCP switch, SCIM/OAuth); the modules are built once and run as services. Built with help from Claude (AI). Licensed under MIT OR Apache-2.0.

Status (0.0.9; 0.0.5 and 0.0.6 are tagged without a release): the library `crates/fs-starter` (words, server gate, frontend pick, exit codes) and the host binary `fs-starter` (`crates/fs-starter-host`). The host opens the window of a program from its description: `fs-starter --description PATH` (PATH is the data package `fs-blueprint new` wrote, a blueprint folder, a `forms/` folder or one file; a bare PATH works too: `fs-starter <package-path>`; the package line names program, skeleton and layout). The host builds the library `Parts` itself: the MCP switch is built and MCP is off (`fs-starter mcp --as ACTOR` ends with `mcp-disabled`, exit 1; the MCP entry itself is not built), and the start hooks run around the window. Single instance is built, per program (`crates/fs-starter-host/src/instance.rs`, ADR 0097): the first start of a program serves the interface `Instance` (`schema/instance.capnp` of fs-interfaces) on `$XDG_RUNTIME_DIR/freesynergy/<name>.window.sock`; on Windows the endpoint is a named pipe per user SID (built, not tested at run time); a second start of the same program hands its words to it, prints `instance-handed-over` and ends with 0 (it is checked with the normal word parser, unknown words are refused with `instance-words-refused`; a hung first instance ends the second with `instance-not-answering`, an unreachable one with `instance-unreachable`; never a second window, nothing is killed). The name is checked as a program name first (`instance-name-invalid`); without `XDG_RUNTIME_DIR` there is no fallback below `/tmp`: one line `single-instance-off` and the program starts anyway. Left out for now: bringing the window to the front, opening the handed-over path in the running window (a start is only received and noted as `instance-start-received`), macOS, killing a hung instance; `--new-instance` is built (see below); a `--picture` start hands over to a running window too (and then draws nothing). Without a running first window `--new-instance` takes `#2` and leaves `.window` free; a later start without the flag becomes `#1`. Session (the host does not call `resume_token` and `fresh` is always false, even with `--fresh`), help and the MCP entry are not built yet and are named once on stderr (`skeleton-part-pending`); the update hook is built (UPD-4, `update/`: replaced own file and module services, heartbeat `save`, crash mark; the own window waits for a calm signal that is not there yet, no `fs-update` source yet; Linux only is proven: on Windows there is no package-lock check and no restart of the own file) and says so on stderr (`update-hook-active`). Plan: ADR draft "Program without build".

Settings (E3, `crates/fs-starter-host/src/open_setting.rs`): the scaffold declares its own settings as DATA in `crates/fs-starter/catalog/settings.json` (`fs.open.when-open`, `fs.rpc.single.ask`, `fs.mcp.enabled`; read with `CatalogFile` of fs-settings). The host opens the settings of the program over the settings service (`ensure_service` + `RpcSettingsStore`) and reads `fs.open.when-open` (`ask` by default). Without the service it says one yellow line (`store-unreachable`) and asks. The value only waits next to the start; opening with it follows (O4). The lock holds one source per library (`tests/pins.rs`; the list of known old doubles is empty).

More windows (`--new-instance`, `crates/fs-starter-host/src/slots.rs`): the flag is a word of the host; the window takes the smallest free endpoint `<name>.window-<k>`, `k` = 2..=9 (the lock of `bind_socket` decides; all taken: `instance-slots-full`). A start without the flag still hands over to the first window (`.window`). The window says `<program>#<k>` as `instance` in `introduce` (the first window is `#1`). With `--picture` the flag takes no place and hands nothing over.

Test data (`--sample-data`, `crates/fs-starter-host/src/sources/sample/`): only the word `--sample-data` asks for them, never a default, never an environment variable or a setting. The host then replaces every `[[source]]` of the description by a `SampleModule` of `fs-forms-testdata`, made from the description (the forms its blocks draw; the section `[sample]` of the description gives the wishes - seed, anchor, count, cases - and without it the defaults of the form declaration hold). The module is held in this process (`fs_rpc::hold_in_process`) and read, held and written like a real module (pages, history with `app.undo`, the port `Writer`), so a window needs no module, no service and no socket; it takes no place of the single instance, starts no update hook and writes no mark of the program (it is no window of the program). Every window with test data says so: the provider is `fake`, and the status line shows "Sample data". A command (a move, a new card) stays in the process: it changes the memory of the window and nothing else; no store, no service, no network is reached (`tests/sample_data.rs`: a spy on the sockets of the process, with a counter-check). Pictures: `fs-starter --description PATH --sample-data --picture FILE.png`. Honest limits: the side strip stays empty (card 19, the strip is fed by `Records::side()`, not by a form), the keys of the commands of a description (`card.move`) do not yet reach the sample module, `app.undo` covers the first source only. Two existing tests changed with this: the picture test of the side strip is `#[ignore]`d with that reason, and the groups picture test no longer compares the sample window pixel for pixel with the fake service (the data are now made from the description).

**Known gap:** RPM: the folders below /usr/share/freesynergy and /usr/libexec/freesynergy are not owned by any package yet (`rpm -qf`: not owned; cargo-generate-rpm cannot build directory assets yet). Windows: der Host findet und startet noch keinen Dienst; Programme mit Modulen laufen unter Windows noch nicht. Sockets/Herzschlag-Grenzen 4, 5-e2e, 7 ungeprüft.

## Auf Deutsch

FreeSynergy starter: der Host, der ein Programm aus seinem Bauplan-Paket (`scaffold.toml` + `forms/` + Texte) startet, ohne es zu kompilieren. Der Host haelt die Teile, die in jedem Programm gleich sind (Sitzung, Update, Darstellung, Hilfe, MCP-Schalter, SCIM/OAuth); die Module werden einmal gebaut und laufen als Dienste. Entstanden mit Hilfe von Claude (KI). Lizenz: MIT OR Apache-2.0.

Stand (0.0.9; 0.0.5 und 0.0.6 sind getaggt ohne Release): die Bibliothek `crates/fs-starter` (Woerter, Server-Tor, Frontend-Wahl, Exit-Codes) und das Host-Binary `fs-starter` (`crates/fs-starter-host`). Der Host oeffnet das Fenster eines Programms aus seiner Beschreibung: `fs-starter --description PFAD` (PFAD ist das Datenpaket, das `fs-blueprint new` schreibt, ein Bauplan-Ordner, ein `forms/`-Ordner oder eine Datei; ein blosser PFAD geht auch: `fs-starter <Paketpfad>`; die Paketzeile nennt Programm, Geruest und Layout). Der Host baut die `Parts` der Bibliothek selbst: der MCP-Schalter ist gebaut und MCP ist aus (`fs-starter mcp --as AKTEUR` endet mit `mcp-disabled`, Exit 1; der MCP-Eingang selbst ist nicht gebaut), und die Start-Haken laufen um das Fenster. Die Einzel-Instanz ist gebaut, je Programm (`crates/fs-starter-host/src/instance.rs`, ADR 0097): der erste Start eines Programms bedient die Schnittstelle `Instance` (`schema/instance.capnp` in fs-interfaces) auf `$XDG_RUNTIME_DIR/freesynergy/<name>.window.sock`; unter Windows ist der Endpunkt eine Named Pipe je Nutzer-SID (gebaut, zur Laufzeit nicht getestet); ein zweiter Start desselben Programms gibt ihm seine Woerter, schreibt `instance-handed-over` und endet mit 0 (geprueft wird mit dem normalen Wort-Leser, unbekannte Woerter werden mit `instance-words-refused` abgelehnt; eine haengende erste Instanz beendet den zweiten Start mit `instance-not-answering`, eine nicht erreichbare mit `instance-unreachable`; nie ein zweites Fenster, nichts wird beendet). Der Name wird zuerst als Programmname geprueft (`instance-name-invalid`); ohne `XDG_RUNTIME_DIR` gibt es keinen Ausweichort unter `/tmp`: eine Zeile `single-instance-off`, das Programm startet trotzdem. Vorerst weggelassen: das Fenster nach vorn holen, den uebergebenen Pfad im laufenden Fenster oeffnen (ein Start wird nur empfangen und als `instance-start-received` vermerkt), macOS, eine haengende Instanz beenden; `--new-instance` ist gebaut (siehe unten); auch ein `--picture`-Start uebergibt an ein laufendes Fenster (und zeichnet dann nichts). Sitzung, Hilfe und der MCP-Eingang sind noch nicht gebaut und werden einmal auf stderr genannt (`skeleton-part-pending`); wo der Host `fs-update` anbindet (Update-Bewaehrung), ist ein offener Punkt (ADR 0105 Offen 9), der Update-Haken ist gebaut (UPD-4, `update/`: ersetzte eigene Datei und Moduldienste, Herzschlag `save`, Absturz-Marke je Fenster; nur Linux ist belegt: unter Windows keine Paketsperren-Prüfung und kein Neustart der eigenen Datei; das eigene Fenster wartet auf ein Ruhe-Signal, das es noch nicht gibt; noch keine `fs-update`-Quelle) und wird auf stderr genannt (`update-hook-active`). Plan: ADR-Entwurf "Programm ohne Build". Die Sitzung ist noch nicht gebaut: der Host ruft `resume_token` nicht auf, und `fresh` ist immer false, auch mit `--fresh` (der `NoopHook` ist harmlos, ein spaeterer Sitzungs-Hook wuerde sonst uebergangen).

Einstellungen (E3, `crates/fs-starter-host/src/open_setting.rs`): das Geruest erklaert seine eigenen Einstellungen als DATEN in `crates/fs-starter/catalog/settings.json` (`fs.open.when-open`, `fs.rpc.single.ask`, `fs.mcp.enabled`; gelesen mit `CatalogFile` aus fs-settings). Der Host oeffnet die Einstellungen des Programms ueber den Einstellungsdienst (`ensure_service` + `RpcSettingsStore`) und liest `fs.open.when-open` (Vorgabe `ask`). Ohne Dienst sagt er eine gelbe Zeile (`store-unreachable`) und fragt. Der Wert liegt nur neben dem Start; das Oeffnen damit folgt (O4). Das Lock hat je Bibliothek eine Quelle (`tests/pins.rs`; die Liste bekannter alter Doppelter ist leer).

Weitere Fenster (`--new-instance`, `crates/fs-starter-host/src/slots.rs`): das Flag ist ein Wort des Hosts; das Fenster nimmt den kleinsten freien Endpunkt `<name>.window-<k>`, `k` = 2..=9 (das Schloss von `bind_socket` entscheidet; alle belegt: `instance-slots-full`). Ein Start ohne Flag gibt weiter an das erste Fenster (`.window`). Das Fenster nennt sich `<programm>#<k>` als `instance` in `introduce` (das erste Fenster ist `#1`). Mit `--picture` nimmt das Flag keinen Platz und gibt nichts ab.

Testdaten (`--sample-data`, `crates/fs-starter-host/src/sources/sample/`): nur das Wort `--sample-data` fragt danach, nie Voreinstellung, nie Umgebungsvariable oder Einstellung. Der Host ersetzt dann jede `[[source]]` der Beschreibung durch ein `SampleModule` aus `fs-forms-testdata`, gemacht aus der Beschreibung (die Formen, die ihre Blöcke zeichnen; der Abschnitt `[sample]` der Beschreibung gibt die Wünsche - Saat, Anker, Anzahl, Fälle - und ohne ihn gelten die Vorgaben der Formdeklaration). Das Modul wird in diesem Prozess gehalten (`fs_rpc::hold_in_process`) und wie ein echtes Modul gelesen, gehalten und beschrieben (Seiten, Verlauf mit `app.undo`, der Port `Writer`); ein Fenster braucht also kein Modul, keinen Dienst und keinen Socket; es nimmt keinen Platz der Einzelinstanz, startet keinen Update-Haken und schreibt keine Marke des Programms (es ist kein Fenster des Programms). Jedes Fenster mit Testdaten sagt es: der Anbieter ist `fake`, die Statuszeile zeigt "Beispieldaten". Ein Befehl (Verschieben, neue Karte) bleibt im Prozess: er ändert den Speicher des Fensters und sonst nichts; kein Speicher, kein Dienst, kein Netz wird erreicht (`tests/sample_data.rs`: ein Spion auf die Sockets des Prozesses, mit Gegenprobe). Bilder: `fs-starter --description PFAD --sample-data --picture DATEI.png`. Ehrliche Grenzen: die Seitenleiste bleibt leer (Karte 19, die Leiste wird von `Records::side()` gespeist, nicht von einer Form), die Schlüssel der Befehle einer Beschreibung (`card.move`) erreichen das Beispielmodul noch nicht, `app.undo` gilt nur für die erste Quelle. Zwei vorhandene Tests haben sich damit geändert: der Bildtest der Seitenleiste ist mit dieser Begründung `#[ignore]`, und der Gruppen-Bildtest vergleicht das Beispielfenster nicht mehr Pixel für Pixel mit dem Fake-Dienst (die Daten werden jetzt aus der Beschreibung gemacht).

**Bekannte Luecke:** RPM: die Ordner unter /usr/share/freesynergy und /usr/libexec/freesynergy gehören noch keinem Paket (rpm -qf: not owned); leere Ordner bleiben nach der Deinstallation liegen. Windows: der Host findet und startet noch keinen Dienst; Programme mit Modulen laufen unter Windows noch nicht. Sockets/Herzschlag-Grenzen 4, 5-e2e, 7 ungeprüft.

## 0.0.8

### English

- SW-5, the host binds the command names: a module names a command only by its contract key (`capability` in `catalog/commands.json`, a line of `capabilities.txt`, e.g. `card.move`); the host binds `<module>.<key>` (`planning.card.move`). The module is the folder the file was read from, never a field the file sets itself. There is NO alias: the host always puts the module name before the key and never interprets it (module `people`, key `people.search` = `people.people.search`; `tasks.create` in `planning` = `planning.tasks.create`); the raw key stays in the registry entry and `invoke` hands the service that key, not the id; an `id` in the file is optional and must equal the derived one (a foreign id: `command-outside-namespace`, `app.`: `command-reserved-prefix`, any other: `command-set-unreadable: command-id-differs`); the same key twice in a file is refused when the file is read; a file read from disk must name only keys of `capabilities.txt` (`fs_interfaces::capabilities`, the list of the fs-interfaces version the host is built with; else `command-set-unreadable: command-capability-unknown`); `--check` is red (`form-command-unknown`, exit 3) for a command channel of a form bound to a key the module does not have (`task.steal`, `planning.task.create`). Contracts and keys of the modules are untouched. New: `registry/read_ids.rs`, `tests/registry_derive.rs`.
- V-5, one way of writing a version need: the host reads a need only as `name@<req>` (`groups@>=0.1.0, <0.2.0`, cargo grammar, comma between comparisons) through `fs_types::interface::InterfaceReq`, and a module version only as three parts (`0.1.0`, `semver::Version`; `0.1` is refused with a cause). The blank form (`groups >=0.1 <0.2`, `groups 0.1`) and a bare name are refused with the message `a need is written name@<req>`; there is no bridge and no second notation. In the library `ContractReq` and `Version3` are gone: `Program::contract` is an `InterfaceVersion`, `fs:requires` of a frontend manifest is an `InterfaceReq` (three numbers in every comparison), the program version is a `semver::Version`. The test data (`tests/data/**`) is on the new form.
- The host says what it read: per source one line `fs-starter: read module=M form=F records=N ms=T provider=P` (`empty` when the service answered with no record, so an empty picture differs from a service that gave nothing); `--check` says forms and commands and that no service was started. One-time commands (`--picture`) end the service they started themselves (a service that was up before is left alone).
- Pins: fs-forms-run and fs-forms-bind on the tag fs-forms v0.0.12 (no longer a commit of a branch); fs-rpc and fs-trusted-path both from the repository FreeSynergy-Net/fs-rpc, tag v0.0.8 (one source); the rest of the FreeSynergy-Net chain as in V-5: fs-types v0.0.6, fs-interfaces v0.0.34, fs-components v0.0.35, fs-objects v0.0.10, fs-release 9eed5c9. The new fields of `FormRow`, `FormData` and `FormRecords` are filled read-only (no writing yet).
- Windows host (WH1, WH3): the name of a program file is made in one place (`layout::program_file`, `service` / `service.exe`; a bare file next to the `.exe` refuses the module with `ambiguous-service`); the check "is this the system's" of a way is the shared crate `fs-trusted-path` (no own copy); Windows anchor is the known folder `FOLDERID_ProgramFiles\FreeSynergy` (not `%ProgramFiles%`), a place without an anchor is `none`, not an empty path; reparse points are not followed on open; a `:` in an exec word is refused; the own `same_file` is replaced by the crate `same-file`.
- One package name: the deb is now called `fs-starter` (like the rpm), no longer `fs-starter-host` (cargo-deb had taken the crate name). `[package.metadata.deb]` sets `name = "fs-starter"` and `replaces`, `conflicts`, `provides` = `fs-starter-host`, so `apt install ./fs-starter_<version>_<arch>.deb` removes the earlier `fs-starter-host` package and takes over its files (upgrade from 0.0.4 and 0.0.7). The file is now called `fs-starter_<version>_<arch>.deb`.
- Correction to 0.0.7 (0.0.7 is tagged and stays as it is; this is the honest note): the 0.0.7 release carries TWO package names. dnf/rpm: `fs-starter` (obsoletes `fs-starter-host`); apt/deb: `fs-starter-host` (file `fs-starter-host_0.0.7-1_<arch>.deb`). Only for the apt side this is a one-time difference: from 0.0.8 on both are `fs-starter`. Whoever installed 0.0.4 or 0.0.7 with apt gets the new name through the upgrade (the old package is removed by Conflicts/Replaces).
- Gate so the names never drift again: `tests/package_names.rs` (the tables of deb and rpm and the `name:` of `release.yml` carry one name) and the job `names` of `package-probe.yml` (reads the name and the replaced package out of the BUILT deb and rpm, both architectures).
